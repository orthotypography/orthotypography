# Releasing orthotypography

Publishing requires explicit authorization covering the release. Merging a pull
request, a green CI run, or a documentation change does not authorize
publication.

Both registries publish `@orthotypography/core` at the version declared in
`deno.json`. JSR publishes the TypeScript source directly; npm receives the ESM
package generated by `@deno/dnt`. The same version must exist on both
registries.

## Publication setup

- The JSR package is linked to this repository.
- npm publishes through trusted publishing (OIDC) from
  `.github/workflows/publish.yml` in the `release` environment. No npm token is
  stored in the repository or its environments; npm `11.5.1` or later on Node
  `22.14.0` or later is installed by the workflow for this purpose, and npm
  attaches provenance to each version.
- Keep the `release` environment protected and restricted to release tags.
- The repository variable `PUBLISH_ENABLED` stays absent or `false` outside an
  authorized publication window. The Publish workflow does nothing unless it
  equals `true`.

Renaming the Publish workflow file or the `release` environment breaks npm
trusted publishing until the package's trusted publisher is updated on npm.
Transferring or renaming the repository has the same effect on npm and also
requires updating the linked repository in the JSR package settings.

## Preparing a release

1. Open a pull request that sets the version in `deno.json`, updates the
   installation example in `README.md`, moves the `Unreleased` entries of
   `CHANGELOG.md` under the new version, and records the prepared state in
   `docs/roadmap.md`.
2. Before merging, run `deno task check`, `deno task test`,
   `deno task publish:check`, and `deno task npm:check`, and confirm that CI
   passes.
3. After merging and once publication is authorized, create a GitHub release
   whose tag is exactly `v` followed by the version in `deno.json`, targeting
   the merged commit on `main`. Prerelease versions must be marked as
   prereleases.
4. Set `PUBLISH_ENABLED` to `true` for the publication window only, and restore
   it afterwards.

The Publish workflow runs on the published GitHub release. It checks that the
tag matches `deno.json`, repeats all four checks at the tag, publishes to JSR
and npm, and waits until both registries expose the version with the expected
npm distribution tag.

## npm distribution tags

npm trusted publishing cannot change distribution tags after publication, so
`scripts/release_metadata.ts` selects the tag passed to `npm publish`:

- every `0.x` version, prereleases included, is published as `latest`, so that
  an unversioned `npm install` resolves to the newest preview;
- from `1.0.0`, stable versions are published as `latest`, and prereleases as
  `alpha`, `beta`, or `next`, so they never displace a stable version.

The final workflow step fails unless npm reports the selected tag on the
published version. An explicit `--tag latest` also moves `latest` to a lower
version, so never publish an older `0.x` version after a newer one.

The `alpha` tag used up to `0.1.0-alpha.2` is no longer updated. Removing it is
a manual registry operation:

```sh
npm dist-tag rm @orthotypography/core alpha
```

## CI

The Publish workflow runs on a pinned runner image (`ubuntu-24.04`), while CI
uses `ubuntu-latest`, so that an image change shows up in CI before it can
affect a release. Move the Publish workflow to a newer image only after CI has
passed on it.

The CI workflow runs the Deno checks on every pull request and push to `main`.
JSR and npm package checks run for changes to `src/`, `deno.json`, `scripts/`,
or the CI and Publish workflows, and on a manual CI dispatch. Documentation-only
pull requests do not build packages.

## Partial publication recovery

The workflow resolves the exact version independently on JSR and npm before
publishing. A version already present is skipped; only a missing registry is
published. The final step waits for both registries to expose the version and
fails if the release remains incomplete.

To resume a partial publication, rerun the failed workflow. If the original run
is no longer available, dispatch `Publish` manually with the existing release
tag. The tag must still equal `v` followed by the version in `deno.json`, and
`PUBLISH_ENABLED` must be `true`. Never increment the version merely to recover
the registry that is missing.

Before resuming, verify that the existing version belongs to this release. The
workflow treats an exact version found on a registry as immutable and
authoritative; it does not overwrite or replace it.
